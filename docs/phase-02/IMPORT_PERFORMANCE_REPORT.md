# تقرير تحسين أداء استيراد بوسطة — المرحلة الثانية

**التاريخ:** 2026-11-05

**الحالة:** نُفذت التحسينات وقيس المسار الكامل للأداة حتى جلب النتائج. الهدف النهائي، 10 ثوانٍ، **غير محقق**. قياس عرض React داخل المتصفح وملف المستخدم الحقيقي الكبير غير متاحين.

## الخلاصة

أُعيد تصميم حل الشحنات والتجار والمراكز إلى عمليات جماعية محدودة الحجم، وأصبحت خريطة الأعمدة خطة ثابتة لكل ورقة ومراجعة Mapping. أضيفت كتابة تكيفية قابلة لإعادة المحاولة، وفحص بصمة محتوى الدفعة، وحماية نشر المراجعات الأحدث. لم تُرخَ قيود المفاتيح أو علاقات المؤسسة.

على ملف اصطناعي واحد حجمه 14,817,681 بايت، وبه 15,120 صف مصدر وورقتان و211 عنوانًا، استغرق المسار المقاس في النسخة النهائية **163,152.523 ms (163.15 ثانية)** من بدء قراءة الملف في Node حتى تنزيل جميع النتائج وفك JSON. كان القياس السابق للتغيير **369,086.097 ms** على الملف نفسه؛ وأظهر تشغيل وسيط بعد التحويل إلى الحل الجماعي **175,622.796 ms**. انخفض عدد استعلامات SQL في النهائي من 50,276 إلى 2,806. المقارنة النهائية ليست متطابقة تمامًا في مسار قرص PHP المؤقت: التجربتان السابقتان استخدمتا إعداد PHP الافتراضي `C:\xampp\tmp`، بينما استخدم التشغيل النهائي مجلدًا على E. لذلك تظل نسبة فرق الزمن وصفًا للقياسات المرصودة وليست تقديرًا سببيًا معزولًا.

تجاوز زمن دفعات الصفوف المتتابعة وحده 125 ثانية في القياس النهائي. ما زال النظام بعيدًا عن هدف العشر ثواني، ولم يُقَس رسم الواجهة داخل المتصفح. لا تعمم الأرقام خارج حد الاختبار المحدد أدناه.

## حد القياس والحمل المرجعي

حد القبول المستهدف للمنتج يبدأ عند تأكيد المستخدم الرفع وقبل قراءة الملف محليًا، وينتهي بعد حفظ جميع بيانات المصدر والمنظمة ونشر التشغيل وجلب الإحصاءات والنتائج الأساسية وظهورها الأول في الواجهة. يشمل القراءة والتحليل والنقل والتحقق والتحويل والحفظ والطابور إن استُخدم وجلب البيانات والرسم الأولي. لا يشمل تسجيل الدخول أو الوقت الذي يسبق تأكيد الرفع.

أمر Benchmark الكامل يقيس من قراءة الملف في Node على الخيط الرئيسي حتى نشر الاستيراد وتنزيل **كل** نتائج التشغيل وفك JSON. يشمل ذلك أكثر من الصفحة الأولى المطلوبة عادة للظهور الأساسي، لكنه لا يقيس متصفحًا أو Worker أو رسم React/DOM. إعداد الطابور الحالي لا يرسل المهمة إليه؛ زمن انتظار الطابور في هذا المسار صفر. لذلك لا يثبت هذا القياس زمن ظهور النتائج داخل المتصفح، ولا يُسجل كاختبار قبول للعشر ثواني.

حد الحمل المقاس في التشغيل النهائي هو **ملف واحد متزامنًا**، نحو 14.8 MB، و15,120 صف مصدر موزعة على ورقتين، و211 عمودًا. العينة تضم تكرارات داخل الدفعة وعبر حدود الدفعات والورقتين، وحقول تواريخ ومال ومحاولات تسليم وقيمًا ناقصة وغير صالحة، ونطاق ورقة يتجاوز البيانات الفعلية بـ5,000 صف. ملف 31.2 MB استُخدم لتحليل المصنف فقط، وليس لاختبار رفع كامل. لا توجد نتيجة لملفين متزامنين أو لملفات أكبر.

الملف الحقيقي المتاح حجمه 12,470 بايت، بورقة واحدة وصف بيانات واحد؛ فُحص للقراءة فقط ولم يُعدّل أو يُستخدم في اختبار كتابة. لم يتوفر ملف حقيقي ممثل بحجم 15 MB.

## التغييرات المنفذة

### معالجة جماعية للهوية والتكرار

- تُجمع بصمات أرقام الشحنات الفريدة في الدفعة، ثم يجري البحث والإدخال واسترجاع المعرّفات جماعيًا. تُجزّأ قوائم المفاتيح إلى مجموعات لا تتجاوز 400 قيمة.
- يُبحث عن اللقطات الموجودة في تشغيل الاستيراد دفعة واحدة؛ وتحافظ المعالجة على ترتيب المصدر واختيار أول ظهور كما كان. يشمل ذلك التكرار داخل الدفعة وبين الدفعات والأوراق السابقة.
- طُبق حل مماثل على التجار والمراكز وأسماء المراكز البديلة، مع إبقاء نطاق المؤسسة والمفاتيح الفريدة.
- تستخدم قراءة `FOR UPDATE` بعد التعارض المتوقع على المفتاح الفريد للحصول على المعرّف المرئي بعد تزامن معاملتين على MariaDB ذات العزل `REPEATABLE READ`.
- عند تنافس ملفين على الشحنة أو التاجر أو المركز نفسه، يبقى سجل الهوية واحدًا لكل كيان ولكل مؤسسة، مع لقطتين مرتبطتين بكل تشغيل.

### خطة أعمدة وتحويلات

- تُبنى خطة الأعمدة مرة لكل ورقة ومراجعة Mapping وتُحفظ في `import_sheets.column_mapping_plan`. تحتوي رقم المصدر والجدول والحقل والنوع ومجموعة محاولة التسليم، وتجاوزات الأعمدة الخاصة، وحقول لوحة المعلومات، وبصمات العناوين والتجاوزات.
- تستخدم الصفوف الخطة مباشرة دون تنظيف عنوان العمود أو البحث في قاموس الحقول الـ211 لكل صف.
- يبقى الصف الخام كاملًا في جدول المصدر. عند فشل التحويل، تُحفظ القيمة الخام ويصدر issue تحذيري بدل إسقاطها.
- تُحفظ أرقام التتبع كنصوص للمحافظة على الأصفار البادئة، وتُحوّل القيم المالية إلى تمثيل عشري دون تخزين مؤقت غير محدود للقيم المتنوعة.
- يُمرر نظام تاريخ Excel 1900/1904 لكل ورقة. تبقى القيمة الرقمية الخام محفوظة، ويُحوّل التاريخ باستخدام المنطقة الزمنية للتشغيل ثم إلى UTC. أُضيف فحص اصطناعي للنظامين.

### كتابة قابلة للتكيف والاستئناف

- تُحدد دفعات قاعدة البيانات وفق عدد الصفوف والروابط وحجم تقريبي للبيانات وحد `max_allowed_packet` وهامش أمان. القيم الافتراضية القصوى: 400 صف، و4,000 رابط، وحجم مستهدف 512 KiB، وهامش 64 KiB قبل حد الحزمة. وتبقى دفعة الطلب الحالية 200 صف كحد أقصى.
- تُحد المعاملات بحجم صفوف الطلب، وتُقسّم كتابات الجداول الداخلية بحسب القيود؛ لا تُستخدم قوائم `IN` غير محدودة.
- يقتصر `ON DUPLICATE KEY UPDATE id=id` على تعارضات الهوية الطبيعية المتوقعة في الشحنات والتجار والمراكز والبدائل. أخطاء الإدخال الأخرى تفشل المعاملة وتُرجع كل كتاباتها.
- لكل دفعة مكتملة بصمة SHA-256 للمحتوى والتجاوزات. إعادة المحتوى ذاته لا تكتب مرة أخرى؛ المفتاح نفسه مع محتوى مختلف يُرفض بـ409. فشل الكتابة يتراجع ثم يمكن إعادة المحاولة.
- يقفل النشر سجل الملف والتشغيل ويرفض تشغيلًا أقدم إذا كان هناك تشغيل أحدث منشور، لمنع وصول مراجعة أقدم متأخرة من استبدال النتيجة الحالية.

### الفهارس

راجعت الفهارس الفعلية على قاعدة الاختبار، وشُغلت `EXPLAIN` المتوافقة مع MariaDB 10.4.28 على البيانات التجريبية. استخدم البحث عن الشحنة `shipments_org_tracking_unique`، والتاجر `businesses_org_external_hash_unique`، واللقطة `snapshots_shipment_run_unique`، والمركز `hubs_org_name_hash_unique`؛ وظهر فهرس المؤسسة/التشغيل/الشدة لاستعلام issues كخطة `ref` تغطي القراءة.

أضافت migration `2026_11_05_000013` بصمة الحمولة وخطة الأعمدة. وحذفت migration `2026_11_05_000014` فهرسين عاديين مكررين بعد التحقق من وجود تغطية مطابقة بمفتاح فريد: `businesses_organization_id_external_id_hash_index` و`snapshots_shipment_history_index`. لم يُحذف قيد فريد أو فهرس لازم لعلاقة، ولم تُضف مجموعة فهارس غير مقاسة.

## البيئة الفعلية وحدودها

- MariaDB الفعلي `10.4.28-MariaDB`. استخدمت القياسات والاختبارات قاعدة MariaDB معزولة على `127.0.0.1:3308`، و`datadir` و`tmpdir` على E. خدمة XAMPP الأصلية على `127.0.0.1:3306` لم تُغيّر؛ وأوقفت خدمة القياس المنفصلة بعد التحقق مع إبقاء ملفات البيانات على E.
- القيم التي قُرئت من خادم MariaDB المعزول: `innodb_buffer_pool_size=16,777,216` B، و`innodb_log_file_size=5,242,880` B، و`innodb_log_buffer_size=8,388,608` B، و`max_allowed_packet=1,048,576` B، و`innodb_flush_log_at_trx_commit=1`.
- Laravel شُغل عبر `php artisan serve` على `127.0.0.1:8000`، وليس Apache. إعداد PHP الفعلي 8.2.4، `memory_limit=512M`، وحدا الرفع وPOST يبلغان 40 MB، وحد API للملف 32 MiB. لا توجد وحدات Xdebug أو Zend OPcache محملة في CLI؛ لم يُقَس OPcache الخاص بـApache.
- نُسخت إعدادات PHP المستخدمة إلى `backend/.local/phase2-php.ini` على E ووُجه `upload_tmp_dir` و`sys_temp_dir` إلى `backend/.local/phase2-tmp`. كانت إعدادات PHP الافتراضية في القياس الأولي تشير إلى `C:\xampp\tmp`؛ هذا اختلاف قرص يجب أخذه في الاعتبار عند مقارنة الأزمنة. كود المشروع وقاعدة البيانات وملفات الاختبار وملفات الرفع المؤقتة للتشغيل النهائي موجودة على E.
- آخر قراءة متاحة للنظام أثناء العمل كانت نحو 6 GiB ذاكرة فعلية متاحة. لم تُجمع سلسلة زمنية لانشغال CPU أو القرص، وكانت عمليات أخرى مثل XAMPP وCodex/Node موجودة؛ لذلك لا يُمثل القياس جهازًا خاملًا مضبوطًا.

## التحقق المنفذ

- Laravel على MariaDB الاختبارية المعزولة: **39 اختبارًا و302 assertion ناجحة**. تتضمن اختبارات بصمة وإعادة الدفعة، رفض محتوى مختلف تحت المفتاح نفسه، استرجاع ما بعد فشل جزئي، نشر المراجعة الأحدث، وتنافس ملفين على شحنة وتاجر ومركز مشتركين.
- شملت اختبارات التخزين حفظ XLS وCSV والملف الخام، وحفظ الأصفار البادئة والقيمة المالية الخام، والتحويلين 1900 و1904، والحفاظ على القيم الخام عند الفشل.
- Pint، و`npm run lint`، و`npm run verify:excel-dates`، و`npm run verify:analytics`، و`npm run build` نجحت. بقي تحذيرا البناء الموجودان سابقًا: استعمال `__dirname` في إعداد Vite وحجم حزمة JS فوق 500 kB. نجح `git diff --check` قبل تحديث هذا التقرير؛ يُعاد بعد توثيق الملفات.
- اجتاز تحليل ملفات XLS وCSV الاصطناعية واختبارات رفعها وتخزينها. بقي تشغيل المتصفح وواجهة React غير مقاس بناءً على توجيه تخطي التحكم في المتصفح.

## إعادة التشغيل

تعمل ملفات التجربة في `backend/.local/import-benchmark/`، وقاعدة Benchmark المنفصلة اسمها `bosta_analysis_benchmark`. لا توجه `IMPORT_BENCHMARK_ENABLED=true` إلى قاعدة التطوير أو بيانات حقيقية. لإعادة تحليل العينات دون كتابة إلى قاعدة البيانات:

```powershell
Set-Location 'E:\data analysis\2026\bosta-analysis'
$env:TEMP = 'E:\data analysis\2026\bosta-analysis\backend\.local\phase2-tmp'
$env:TMP = $env:TEMP
npm run benchmark:imports -- profile backend/.local/import-benchmark/synthetic_bosta_15mb_211_columns.xlsx
npm run benchmark:imports -- profile backend/.local/import-benchmark/synthetic_bosta_compatibility.xls
npm run benchmark:imports -- profile backend/.local/import-benchmark/synthetic_bosta_compatibility.csv
```

لتشغيل Benchmark كامل، شغّل MariaDB المعزولة مستخدمًا `backend/.local/phase2-mariadb/server.ini`، ثم اضبط Laravel على `bosta_analysis_benchmark` والمنفذ 3308، وفعّل `IMPORT_BENCHMARK_ENABLED=true` و`IMPORT_BENCHMARK_DATABASE=bosta_analysis_benchmark` قبل تشغيل `php artisan serve --host=127.0.0.1 --port=8000`. عيّن `IMPORT_BENCHMARK_URL` و`IMPORT_BENCHMARK_ORGANIZATION` وبيانات اعتماد حساب Benchmark محليًا في جلسة PowerShell (لا تضع كلمة المرور في سجل أوامر محفوظ)، ثم شغّل:

```powershell
npm run benchmark:imports -- benchmark backend/.local/import-benchmark/synthetic_bosta_15mb_211_columns.xlsx
```

استخدم مؤسسة اصطناعية جديدة لكل قياس كامل. للمقارنة البنيوية بين تشغيلين منشورين، شغّل مع متغيرات الاتصال نفسها:

```powershell
& 'C:\xampp\php\php.exe' -d memory_limit=1536M backend/scripts/compare_import_benchmarks.php phase2-before phase2-final-e-date
```

يحصر middleware تفعيل القياس في قاعدة Benchmark المحددة، والقياس التجميعي معطل افتراضيًا. القياس لا يسجل SQL أو محتوى الخلايا.
