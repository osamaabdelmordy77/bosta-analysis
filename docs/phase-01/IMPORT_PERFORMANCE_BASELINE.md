# Baseline أداء استيراد ملفات Bosta — المرحلة الأولى

**تاريخ القياس:** 2026-11-05

**الحالة:** قياس API وخط المعالجة مكتمل على عينة اصطناعية معزولة؛ قياس واجهة المتصفح الفعلي غير منفذ بناءً على توجيه المستخدم بتخطي التحكم في المتصفح. لا يثبت هذا التقرير هدف العشر ثواني.

## الخلاصة

قيس المسار من قراءة عينة XLSX محليًا في Node، مرورًا بطلب الرفع ودفعات الصفوف والنشر، حتى تنزيل صفحات نتائج الشحنات والإعدادات وقائمة الملفات وفك JSON. استغرق هذا المسار **213,341.876 ms (213.34 ثانية)** لعينة اصطناعية بحجم 14,817,681 بايت، و15,120 صف مصدر، وورقتين، و211 عنوانًا. أُعيدت 15,028 شحنة منشورة كاملة إلى العميل. القراءة وفك المصنف في هذا القياس أُجريا في Node على الخيط الرئيسي، وليس داخل متصفح أو Worker.

الهدف التشغيلي الذي ينبغي استخدامه للمقارنات اللاحقة هو: **ملف واحد في كل مرة، حتى 15 MB تقريبًا، و15,000 صف مصدر أو أكثر قليلًا، وورقتان، و211 حقلًا، على localhost ببيئة XAMPP المذكورة أدناه؛ تبدأ الساعة عند تأكيد المستخدم رفع الملف وقبل أول قراءة محلية، وتنتهي بعد استلام الإحصاءات والصفحة الأولى اللازمة لظهور النتائج الأساسية الصحيحة في الواجهة.** يدخل في المدة قراءة الملف، التحليل، الرفع، الانتظار إن أُضيفت طوابير، التحقق والتحويل، الحفظ الكامل للمصدر والبيانات المنظمة، النشر، جلب الإحصاءات والنتائج، والرسم الأولي. لا يدخل فيها تسجيل الدخول أو وقت اختيار المستخدم للملف قبل التأكيد أو تفاعلات التحليل اللاحقة. قياس المرحلة الحالية ينتهي عند اكتمال تنزيل **كل** نتائج هذا التشغيل وفك JSON، ولذلك فهو أوسع من حد النتائج في التعريف، لكنه لا يتضمن متصفح React ولا الرسم الأولي. لا توجد نتيجة قبول للعشر ثواني بعد.

هذا حد حمل مرجعي لملف واحد متزامنًا، وليس ضمانًا لملفات أكبر أو لمستخدمين متزامنين. الملف الحقيقي المتاح في المستودع صغير جدًا بحيث لا يصلح لهذه المقارنة.

إجمالي 97 طلب API: طلب رفع واحد، و76 دفعة، وطلب نشر واحد، و19 طلب نتيجة (قائمة الملفات والإعدادات و16 صفحة للشحنات المنشورة وصفحة legacy واحدة). مجموع `Content-Length` الذي شاهده PHP هو 38,704,373 بايت؛ تقدير أجسام JSON لطلبات الدفعات 23,877,712 بايت؛ وحجم استجابات JSON المقاس 6,909,756 بايت. فروق النقل تشمل multipart headers والبيانات الوصفية. أزمنة الطلبات المتوازية للنتائج لا تُجمع على أنها زمن حائطي.

مجاميع الخادم على الطلبات المترابطة: 149,697.124 ms زمن طلب PHP، و50,276 استعلام SQL بمجموع 58,903.490 ms، وأقصى ذاكرة PHP مقاسة 48,234,496 B. وبلغت مجاميع المراحل داخل PHP 62,871.017 ms لربط الصفوف والتحقق، و29,708.718 ms لإدراج الدفعات. زمن SQL تراكمي ومتداخل مع مراحل التطبيق؛ لا يُضاف إلى زمنها. بلغ RSS الأقصى لعملية Node نحو 500,488 KiB، وكانت `heapUsed` بعد اكتمال النتائج 85,245,208 B. هذا ليس قياس ذاكرة متصفح أو Worker.

تحقق استعلام قراءة بعد النشر من النتائج المخزنة: 15,120 صف مصدر محفوظًا، و15,028 snapshot منشورًا، و76 تكرارًا، و16 صفًا مرفوضًا، و304 issue منها 288 تحذيرًا. حاصل جمع المقبول والمكرر والمرفوض يساوي جميع صفوف المصدر. عدد الشحنات المسترجعة من واجهة النتائج كان 15,028.

### تحليل مواضع الزمن

1. طلبات الدفعات المتتابعة: 167.4 ثانية، نحو 78.5% من الإجمالي المرصود. عدد الرحلات الشبكية 76، مع تحليل/تحقق وإدراج لكل دفعة.
2. جلب النتائج كاملة: 33.7 ثانية، نحو 15.8%، مع 19 طلبًا وقرابة 6.91 MB استجابات JSON. تصحيح مؤشر الترقيم سمح بإكمال الصفحات؛ قبل التصحيح كان العميل يعيد الصفحة الأولى ولا يصل إلى كل الصفوف.
3. التحليل والرفع: 5.85 و5.94 ثانية على الترتيب، كل منهما نحو 2.7% من الزمن الكلي.
4. داخل الخادم، ربط الصفوف والتحقق والإدراج استهلكا 62.9 و29.7 ثانية إجمالًا عبر الدفعات. لا توجد أرقام CPU/قرص معزولة تثبت سببًا أدق. مجموع زمن SQL 58.9 ثانية ويبين كلفة قاعدة البيانات، لكنه يتداخل مع زمن مراحل الخادم ولا يمثل زمنًا إضافيًا مستقلًا.
5. النشر أقل من 0.4 ثانية. الانتظار في الطابور صفر في التصميم المقاس.

هذه القياسات تشغيل كامل واحد بعد إصلاح الترقيم، وليست متوسطًا أو p95. بعده شُغّل أمر profile مستقل على ملف الـ15 MB نفسه؛ قرأ الملف في 56.063 ms وحلله في 8,680.814 ms، مع RSS مرصود 435,068,928 B. اختلاف التحليل بين 5.85 و8.68 ثانية يوضح أن عينة التشغيل والقياس حساسة لحمل الجهاز، ولا يبرر رقمًا ثابتًا للمحلل. إضافة القياس التجميعي نفسها قد تضيف حملًا صغيرًا غير مفصول عن النتيجة. يلزم تكرار بارد/دافئ قبل مقارنة فروق صغيرة.

## البيئة الفعلية وقت القياس

- الاتصال الفعلي للتطبيق قبل تشغيل الاختبار كان XAMPP MariaDB على `127.0.0.1:3306`، الإصدار `10.4.28-MariaDB`. جرى إنشاء/استخدام قاعدة Benchmark منفصلة للأداة؛ ملف `.env` المحلي للتطوير يشير إلى `bosta_analysis_local`.
- قرأ الاستعلام من الخادم نفسه: `innodb_buffer_pool_size=16,777,216` B (16 MiB)، و`innodb_log_file_size=5,242,880` B (5 MiB)، و`max_allowed_packet=1,048,576` B (1 MiB)، و`tmp_table_size=16,777,216` B، و`innodb_flush_log_at_trx_commit=1`. القيمتان السابقتان في `my.ini` تأكدتا كقيم تشغيل فعلية.
- PHP CLI المستخدم: XAMPP PHP 8.2.4، `memory_limit=512M`، و`max_execution_time=120`، و`upload_max_filesize=40M`، و`post_max_size=40M`. حد API في التطبيق 32 MiB. امتداد ZIP غير مفعّل في CLI؛ فك XLSX يجري في Node لا PHP. لم يظهر Xdebug أو Zend OPcache في وحدات CLI. Apache كان موجودًا عبر `httpd.exe` مع `php_module` على 80/443، لكن قياس الاستيراد نفسه شُغّل عبر `php artisan serve` على 127.0.0.1:8000، وهو خادم التطوير، لا Apache.
- إعداد Queue هو database، لكن مسار الاستيراد الحالي لا يرسل مهمة؛ لا يوجد انتظار أو عامل Queue في المسار المقاس.
- عينة الذاكرة المتاحة في النظام قبل القياس كانت قرابة 5,689 MiB. مساحة C: المتاحة تفاوتت بين نحو 1.75 GB قبل حمل التجارب، و846 MB كأدنى قراءة لاحقة، و1.197 GB عند الفحص النهائي بعد انتهاء العمليات. جرى توليد ملفات وقاعدة بيانات اصطناعية أثناء القياس ولم تُحذف. كانت عمليات XAMPP وCodex/Node الأخرى موجودة؛ لم تتوفر قراءة موثوقة لمعدل انشغال القرص/CPU. لذلك لا تمثل هذه نتيجة على جهاز خامل أو بيئة إنتاج مضبوطة.
- لم يُفحص OPcache الخاص بـApache عبر `phpinfo`، ولم تُجمع مقاييس I/O أو CPU مستمرة. لا يجوز استنتاج حالتهما أو غيابهما من إعداد CLI.

## السلوك الصحيح المحفوظ والتحقق

- التخزين الأصلي يحفظ بايتات الملف وبصمة SHA-256؛ اختبار `ImportStorageTest` يغطي البصمة وقيم المصدر. قياس العينة تحقق من تطابق بصمة الملف الاصطناعي مع `import_files.sha256`، ومن العدد الدقيق لصفوف المصدر ولقطات الشحنات بعد النشر.
- صفوف المصدر تحفظ مع معرّف الورقة ورقم صف المصدر والقيم الخام. القياس أرسل أسماء الأوراق ومواقعها وعناوينها الأصلية في كل من الورقتين؛ واختبارات التخزين الحالية تغطي قيم المصدر الخام والتكرارات.
- لم تُغيّر قواعد كشف التكرار، حالات المراجعة، إعادة المحاولة أو النشر أو الأرشفة. تحتفظ المفاتيح الفريدة بنطاق المؤسسة والتشغيل كما في migrations، وتوجد اختبارات تكامل للتكرار والنشر والأرشفة/إعادة المحاولة.
- فُحصت فهارس migrations ذات الصلة: `import_source_rows_idempotency_unique` يمنع تكرار رقم صف المصدر داخل الورقة والتشغيل؛ `shipments_org_tracking_unique` يحفظ منع تكرار tracking ضمن المؤسسة؛ `snapshots_shipment_run_unique` يمنع لقطة شحنة مكررة داخل التشغيل. توجد فهارس المؤسسة/التشغيل والمركز والتاجر وحالة التسليم على snapshots، ولا يضيف هذا التغيير فهرسًا أو يبدّل تعريفًا قائمًا.
- فُحصت حدود الصلاحية: بدء الاستيراد وإضافة الدفعة والنشر والأرشفة تتطلب `imports.manage`، والأرشفة الكلية تتطلب `data.manage`؛ قراءة الشحنات تتطلب `shipments.view_all` أو `shipments.view_assigned` وتُضيّق بـ`HubAccessService`، وقراءة legacy تتطلب `shipments.view_all`. اختبارات `AuthAccessTest` و`DataIntegrityTest` تغطي العزل والوصول؛ لم تتغير سياسات الصلاحيات.
- تحققت أداة `verify:analytics` من إجماليات الشحنات والعناصر، والمراكز الصفرية، واتجاهات اليوم/الشهر، ومجموعة فلاتر المركز والتاجر والشهر ونطاق التاريخ، واختيار أساس المركز الحالي أو المعين. اجتازت اختبارات الصلاحيات والعزل الموجودة. لم يُغيّر إعداد الصلاحيات.
- كشف القياس عن خلل pagination حقيقي: كان `nextCursor()` يُقرأ بعد تحويل paginator إلى payload، فيصبح مؤشر الصفحة التالية غير متاح. حُفظ المؤشر من paginator الخام قبل تحويل الصفوف، وأضيف معرّف الصف المتوقع لاستعمال المؤشر. أكمل اختبار API بعد الإصلاح تنزيل 15,028 صفًا، وتظهر المجاميع المحفوظة أعلاه. هذا تصحيح صحة بيانات/إكمال النتائج، وليس تحسينًا لتغيير قواعد العمل.
- لم يُنفذ اختبار العرض في المتصفح وفق توجيه المستخدم؛ لا توجد مقارنة مرئية لأرقام الداشبورد من مسار React الكامل ولا قياس ذروة ذاكرة Worker. هذه فجوة مقصودة ومذكورة، وليست تقديرًا.

## القياس القابل لإعادة التشغيل

الأوامر التالية تستخدم ملفات اصطناعية فقط. أنشئ قاعدة بيانات MariaDB جديدة باسم `bosta_analysis_benchmark` أو استخدم القاعدة المعزولة القائمة، وطبّق migrations عليها، وجهّز حسابًا ومؤسسة اصطناعيين جديدين لكل تشغيل كامل. لا توجّه `IMPORT_BENCHMARK_ENABLED=true` إلى قاعدة تطوير أو مستخدمين حقيقيين؛ middleware يرفض أي اسم قاعدة غير القيمة المحددة.

```powershell
npm run benchmark:imports -- generate 15120 220
npm run benchmark:imports -- profile backend/.local/import-benchmark/synthetic_bosta_15mb_211_columns.xlsx
npm run benchmark:imports -- profile backend/.local/import-benchmark/synthetic_bosta_compatibility.xls
npm run benchmark:imports -- profile backend/.local/import-benchmark/synthetic_bosta_compatibility.csv
npm run benchmark:imports -- generate 15120 1400
npm run benchmark:imports -- profile backend/.local/import-benchmark/synthetic_bosta_limit_211_columns.xlsx
```

لإعادة تشغيل المسار الكامل، شغّل Laravel مؤقتًا على 8000 مع `DB_DATABASE=bosta_analysis_benchmark` و`IMPORT_BENCHMARK_ENABLED=true` و`IMPORT_BENCHMARK_DATABASE=bosta_analysis_benchmark`. في PowerShell منفصل، عيّن `IMPORT_BENCHMARK_EMAIL` و`IMPORT_BENCHMARK_PASSWORD` لحساب الاختبار، و`IMPORT_BENCHMARK_ORGANIZATION` إلى slug مؤسسة اصطناعية جديدة، ثم شغّل:

```powershell
npm run benchmark:imports -- benchmark backend/.local/import-benchmark/synthetic_bosta_15mb_211_columns.xlsx
```

تُطبع نتيجة JSON شاملة؛ يسجل Laravel حدثًا تجميعيًا واحدًا لكل طلب مترابط دون SQL أو قيم خلايا. يرفض الأمر تشغيلًا سبق استيراد الملف نفسه في المؤسسة ذاتها كي لا يصف إعادة استخدام idempotent على أنها قياس معالجة كامل. استخدم مؤسسة اختبار جديدة لكل تشغيل، واحتفظ بقاعدة وملفات الاختبار؛ لا يلزم أي حذف. `IMPORT_BENCHMARK_ENABLED` معطل افتراضيًا. مسار React لديه قياس اختياري عند تشغيل Vite بـ`VITE_IMPORT_BENCHMARK=1` والـBackend بالعلامة نفسها، لكنه لم يُقَس هنا.

## الاختبارات وحدود الاستنتاج

- `npm run lint`، `npm run build`، `npm run verify:analytics`، Pint، واختبارات Laravel: **38 اختبارًا و244 assertion**؛ كلها نجحت. بقي تحذيرا Vite المعتادان (`__dirname` وحجم الحزمة). اجتاز فحص diff whitespace.
- قاعدة `bosta_analysis_test` منفصلة عن قاعدة التطوير، ورفض middleware تفعيل القياس على قاعدة غير `bosta_analysis_benchmark`. فحوص الكتابة والحمل على قاعدة الاختبار/الـBenchmark المعزولة فقط.
- لم تُقَس واجهة React أو عامل المتصفح أو عرض DOM أو حزمة ملفات متعددة متزامنة. لا يوجد ملف حقيقي متاح ممثل بحجم 15 MB. ملف 31 MB تحليل محلي فقط، وليس رفعًا كاملًا.
- لا تثبت المرحلة بلوغ 10 ثوانٍ؛ القياس الكامل المتاح هو 213.34 ثانية في ظروف localhost المذكورة. أي قبول لاحق يجب أن يشمل حد بداية ونهاية القياس أعلاه، ويعيد البيانات الصحيحة، ويذكر حجم الملف وعدد الأوراق والصفوف ومستوى التزامن وعدد التكرارات وقياسات الزمن والذاكرة، مع عدم خلط استجابة HTTP أو إدراج Queue بمدة معالجة الملف كاملة.
