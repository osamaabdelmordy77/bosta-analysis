# تقرير نقل استيراد المصنف إلى الخادم — المرحلة الثالثة

**التاريخ:** 2026-11-05

**الحالة:** تدفق الاستيراد بالخلفية منفذ ومتحقق على MariaDB اختبارية معزولة. هدف العشر ثواني **غير محقق**.

## النتيجة المقاسة

قيس التدفق من قراءة ملف العينة في عميل Node إلى تحميل بيانات النتائج وفك JSON. يبدأ حد القبول النهائي للمنتج عند تأكيد المستخدم الرفع، وينتهي بعد نشر كل بيانات المصنف وجلب النتائج الأساسية وظهورها للمستخدم. لا يشمل تسجيل الدخول، ويجب أن يشمل عرض React/DOM عند القبول النهائي. هذا القياس ينتهي بعد تحميل بيانات التطبيق من API؛ لم تُشغّل واجهة المتصفح أو تقِس React بناءً على توجيه المستخدم بتخطي التحكم في المتصفح.

| المرحلة | الزمن |
|---|---:|
| قراءة ملف العميل | 25.249 ms |
| إرسال طلب ملف واحد مع multipart | 4,979.986 ms |
| انتظار الطابور وملاحظة اكتمال العامل | 112,985.442 ms |
| إعادة جلب بيانات التطبيق وفك JSON | 39,433.954 ms |
| **الإجمالي حتى تحميل النتائج** | **157,488.633 ms (157.49 ثانية)** |
| انتظار الطابور كما قاسه العامل | 580.605 ms |
| زمن العامل حتى النشر | 111,960.345 ms |
| زمن الطابور إلى النشر | 112,540.955 ms |

إذًا لا يقترب هذا الحمل من هدف 10 ثوانٍ بعد. وبالمقارنة الوصفية مع قياس المرحلة الثانية النهائي على بصمة الملف نفسها (163.15 ثانية)، كان الإجمالي أقل بنحو 3.5% في تشغيل واحد لكل مرحلة. هذه ليست مقارنة إحصائية ولا تثبت أن النقل إلى العامل سرّع التنفيذ؛ تغيّر توزيع العمل وعدد نقاط القياس، ولم تُنفذ تكرارات باردة ودافئة.

سجل Laravel 99 طلب HTTP يحمل معرّف الارتباط؛ منها 79 استعلام حالة، وطلب رفع واحد، وطلبات النتائج. يعد Node 101 طلبًا شاملًا طلب CSRF وتسجيل الدخول اللذين يسبقان نطاق الرفع. حجم طلب الملف الذي استلمه PHP 14,818,250 بايت، وحجم أجسام الاستجابات المرصودة 7,296,707 بايت. استهلاك ذاكرة المتصفح ورسم DOM غير مقاسين.

في العامل، استغرق فحص المصنف 1,085.448 ms، ومرحلة القراءة والتحقق والتحويل والحفظ 110,557.535 ms. ضمن القياس المتداخل نفسه: حفظ الدفعات 34,751.742 ms، تجهيز القيم والتحقق 12,634.253 ms، ربط التجار والمراكز 8,084.421 ms، حل هوية الشحنات 3,864.667 ms، وتحويل التواريخ 2,341.095 ms. أكبر تكلفة هي معالجة الصفوف وحفظها؛ يليها جلب كل النتائج، الذي استغرق 39.43 ثانية من جهة العميل و31.99 ثانية كزمن خادم تراكمي لصفحات الشحنات. لا تُجمع أزمنة SQL ومراحل PHP بعضها فوق بعض لأنها متداخلة.

## ما تغير في مسار الاستيراد

- ترفع الواجهة الملف مرة واحدة باستخدام XHR وتعرض تقدم البايتات منفصلًا عن تقدم العامل. لم تعد تقرأ المصنف الكامل أو ترسل صفوفه في طلبات متتابعة في المسار التشغيلي.
- يحفظ API الأصل في قرص خاص خارج الجذر العام ويتحقق من حجمه وبصمته. يسجل المرجع والخيارات والتشغيل ومهمة قاعدة البيانات في معاملة واحدة؛ Payload المهمة لا يحتوي المصنف أو الصفوف.
- حالات التشغيل تشمل `queued`, `parsing`, `importing`, `finalizing`, `completed`, `failed`. يبقى الإجمالي مجهولًا حتى يُقاس فعليًا. لا يصبح التشغيل مكتملًا إلا بعد تطابق أعداد الصفوف والأجزاء واللقطات ونشر المراجعة وتحديث مؤشر الملف النشط.
- يستطيع العامل متابعة تشغيل بعد فشل جزئي بأمان؛ الدفعة المكتملة لا تعاد كتابتها، ويمنع قفل التشغيل عاملين من تنفيذ المفتاح نفسه معًا. زمن المهلة 3,600 ثانية، و`retry_after` الافتراضي 3,900 ثانية، وثلاث محاولات افتراضيًا.
- لا تُحذف أو تُنقل تلقائيًا BLOBs القديمة. يستطيع المسار الجديد قراءة الأصل القديم وبناء نسخة مؤقتة متحقق منها على التخزين الخاص. أضيفت migration مرقمة جديدة لحالات المعالجة ومراجع التخزين دون تعديل migration مطبقة.
- بعد إعادة فتح الصفحة، يستعيد API آخر الحالات. إعادة رفع الملف نفسه بالإعدادات نفسها آمنة، وفشل التشغيل يظهر مع خيار إعادة محاولة. اختبار المراجعتين يرفع مراجعتين مختلفتين للاسم نفسه قبل تشغيلهما، وينشر الأحدث أولًا ثم يثبت رفض نشر الأقدم.

## قارئ المصنف ودعم الصيغ

الإصدارات الفعلية: PHP 8.2.4، Laravel 12.70.2، OpenSpout 4.28.5، وPhpSpreadsheet 5.10.0. امتدادات `zip`, `xmlreader`, `mbstring`, و`pdo_mysql` مفعلة؛ لم تكن وحدتا Xdebug وOPcache محملتين في CLI.

- OpenSpout يقرأ XLSX وCSV تدريجيًا؛ استخدمه المسار لهذه الصيغ لتجنب مصفوفة خلايا كاملة. في ملف XLSX الاصطناعي 14.8 MB سجّل قياس القارئ المنفصل 39.079 ثانية وذروة 4 MiB أثناء فحص جميع الخلايا وحساب البصمات.
- OpenSpout لا يقرأ تنسيق XLS القديم، لذلك يستخدم XLS مسار PhpSpreadsheet مع مرشح صفوف محدود. عينة XLS اصطناعية من 100 صف و211 عمودًا استغرقت 1.284 ثانية و20 MiB. مرشح PhpSpreadsheet على ملف XLSX المرجعي استغرق أكثر من 121 ثانية ووصلت ذاكرته إلى نحو 798 MiB، لذلك لم يُستخدم لمسار XLSX.
- يحتفظ CSV بالفواصل والاقتباسات والأسطر الجديدة داخل الخلايا، مع اكتشاف الفاصل والترميز. اختبر XLS وCSV بقراءة القيم متعددة الأسطر وأرقام الصفوف.
- تحفظ قراءة XLSX أرقام التاريخ الخام، وتدعم نظامي Excel 1900 و1904 والمنطقة الزمنية. لا يعيد التطبيق حساب الصيغ؛ يستخدم نتيجة الصيغة المخزنة في المصنف، عبر القيمة المحسوبة/المخزنة التي يعرضها القارئ. إذا لم توجد نتيجة مخزنة، لا يجري اختراع قيمة.
- الاختيار متوافق مع PHP والإصدارات المحلية ونتائج القياس أعلاه. المراجع الرسمية: [OpenSpout](https://github.com/openspout/openspout)، [PhpSpreadsheet file reading](https://phpspreadsheet.readthedocs.io/en/latest/topics/reading-files/)، و[PhpSpreadsheet memory saving](https://phpspreadsheet.readthedocs.io/en/latest/topics/memory_saving/).

## البيئة الفعلية وعزل البيانات

- Laravel المحلي يتصل فعلًا بـ`bosta_analysis_local` على `127.0.0.1:3306`، MariaDB `10.4.28-MariaDB`. تحقق الاتصال باستعلام PDO عبر إعداد Laravel وبعميل MariaDB؛ وجد 15 migration وجدول `import_runs`. آخر migration مطبق هو 012؛ migrations المرحلة الثانية/الثالثة 013–015 لم تُطبق على القاعدة الأصلية، وتلزم قبل تشغيل مسار الكود الجديد عليها. لم تنفذ الاختبارات أو الـBenchmark كتابة على هذه القاعدة.
- واجه `artisan db:show` جدول `performance_schema.session_status` غير المتاح في إعداد MariaDB هذا؛ تحقق الاتصال باستخدام `SELECT DATABASE(), VERSION(), @@port` عبر Laravel نفسه بدل الاعتماد على الأمر.
- جميع قواعد الاختبار والـBenchmark على MariaDB معزولة بمنفذ 3308 وملفاتها و`tmpdir` وملفات PHP المؤقتة والتخزين الخاص على E. إعداد الخادم المقاس: `max_allowed_packet=1,048,576`, `innodb_buffer_pool_size=16,777,216`, `innodb_log_file_size=5,242,880`, `innodb_log_buffer_size=8,388,608`, و`innodb_flush_log_at_trx_commit=1`.
- شُغل API عبر `artisan serve` على `127.0.0.1:8013` وعامل Queue واحد منفصل. أُوقفا بعد انتهاء القياس. لا توجد عينة تزامن حمل في هذا الـBenchmark ولا سلسلة زمنية لانشغال CPU أو القرص؛ كانت خدمة MariaDB الأصلية على 3306 موجودة أثناء الاختبار.
- ملفات المشروع والمصنف الاصطناعي وقواعد الاختبار وبيانات الاختبار والمخرجات على E. PHP التنفيذي المحلي ما زال `C:\xampp\php\php.exe`.

## الاختبارات والتحقق

- `php artisan test --env=testing`: **41 اختبارًا و330 assertion ناجحة** على `bosta_analysis_stage3_test` في MariaDB المنفصلة على E.
- اختبار تكامل رفع API شغّل العامل فعليًا عبر `queue:work --once`، وتحقق من استعادة الحالة بعد إعادة فتح API، والرفع المكرر، والنسخة الخاصة والبصمة، ومصدر الصفوف، والنشر. اختبر فشلًا بعد حفظ أول 400 صف، ثم إعادة محاولة آمنة دون تكرار. اختبر أيضًا مراجعتين رُفعتا معًا ونشر الأحدث قبل الأقدم.
- اختبار تزامن ملفين مستقلين على رقم شحنة وتاجر ومركز مشترك أثبت بقاء هويات المؤسسة واحدة وربط اللقطات بكل تشغيل.
- اختبارات قارئ XLSX وXLS وCSV تشمل البصمة الخام للتاريخ، الأصفار البادئة، تعدد الأوراق، وأسطر CSV المقتبسة متعددة الأسطر.
- `npm run lint`, `npm run build`, PHP lint للملفات المعدلة، `node --check` لأدوات Benchmark، و`git diff --check` نجحت. بقي تحذيرا Vite المعروفان: `__dirname` وحزمة JavaScript بعد الضغط أكبر من 500 kB. لم يتوفر Composer CLI في PATH، لذا تم التحقق من JSON في `composer.json` دون ادعاء نجاح `composer validate`.
- لم يُستخدم المتصفح أو ملف المستخدم الحقيقي في الكتابة؛ بناء الواجهة وفحوص الأنواع ناجحة، لكن الرندر الفعلي داخل المتصفح وقياس إغلاق الصفحة بصريًا غير منفذين وفق توجيه المستخدم.

## إعادة تشغيل القياس

توجد العينة الاصطناعية والتقارير التفصيلية في `backend/.local/import-benchmark/` على E. شغّل MariaDB المعزولة بإعداد `backend/.local/phase2-mariadb/server.ini`، ثم عيّن متغيرات PowerShell التالية على قاعدة Benchmark فقط في كل طرفية API وعامل:

```powershell
$env:PHPRC = 'E:\data analysis\2026\bosta-analysis\backend\.local\phase2-php.ini'
$env:APP_ENV = 'local'
$env:DB_CONNECTION = 'mysql'
$env:DB_HOST = '127.0.0.1'
$env:DB_PORT = '3308'
$env:DB_DATABASE = 'bosta_analysis_stage3_benchmark'
$env:DB_USERNAME = 'root'
$env:DB_PASSWORD = ''
$env:QUEUE_CONNECTION = 'database'
$env:DB_QUEUE = 'imports'
$env:DB_QUEUE_RETRY_AFTER = '3900'
$env:IMPORT_BENCHMARK_ENABLED = 'true'
$env:IMPORT_BENCHMARK_DATABASE = 'bosta_analysis_stage3_benchmark'
$env:IMPORT_BENCHMARK_ORGANIZATION = 'phase3-benchmark'
$env:IMPORT_FILE_STORAGE_PATH = 'E:/data analysis/2026/bosta-analysis/backend/.local/stage3-benchmark-storage/imports'
$env:IMPORT_READER_TEMP_PATH = 'E:/data analysis/2026/bosta-analysis/backend/.local/stage3-benchmark-storage/temp'
```

في طرفية API شغّل `php artisan serve --host=127.0.0.1 --port=8013`. في طرفية ثانية جهّز حسابًا اصطناعيًا معزولًا بعد تعيين `IMPORT_BENCHMARK_EMAIL` و`IMPORT_BENCHMARK_PASSWORD` محليًا، ثم شغّل العامل:

```powershell
php scripts/prepare_import_benchmark.php
composer queue:imports
```

من جذر المستودع، عيّن `IMPORT_BENCHMARK_URL=http://127.0.0.1:8013` و`IMPORT_BENCHMARK_ORIGIN=http://localhost:3000` وبيانات حساب Benchmark، ثم:

```powershell
npm run benchmark:import-pipeline -- backend/.local/import-benchmark/synthetic_bosta_15mb_211_columns.xlsx
```

يحفظ الأمر JSON تحت `backend/.local/import-benchmark/phase3-results/`. لا تقم بتفعيل قياس Benchmark على `bosta_analysis_local`، ولا تستخدم الملف الحقيقي كمدخل لهذا الأمر.

## ما لم يُثبت بعد

- لا يحقق النظام هدف 10 ثوانٍ: بلغ القياس 157.49 ثانية حتى جلب النتائج. عنق الزجاجة الأول معالجة الصفوف وحفظها، والثاني تحميل كل النتائج إلى التطبيق.
- لا يوجد قياس للمظهر الفعلي أو لحظة رندر DOM، لأن تحكم المتصفح تم تخطيه. يلزم قياس ذلك لاحقًا قبل اعتماد حد 10 ثوانٍ النهائي.
- لم يُجر اختبار حمل متزامن لملفين من تدفق API/Queue الكامل، ولا اختبار كامل لملف 31.2 MB. اختبار التزامن الموجود يغطي ملفين مستقلين يتشاركان رقم شحنة وتاجرًا ومركزًا.
- لم يُرفع الملف الحقيقي إلى أي قاعدة؛ قبول العشر ثواني على ملف المستخدم لم يُثبت، والقياس الوحيد الممثل حتى الآن اصطناعي وعلى عامل واحد.
